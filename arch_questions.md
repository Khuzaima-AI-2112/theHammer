# The Hammer — Production Architecture: Open Questions
## Role: Senior GCP Architect & SRE

_Generated by reviewing `sprintplan2.md` against production readiness criteria for a multi-role GCP platform (Cloud Run · Firestore · GCS · Secret Manager)._

---

## 1. Compute & Cloud Run

### 1.1 Service Topology
- How many Cloud Run **services** will exist? The sprint plan mentions a backend API, an Admin Portal, and an FFmpeg export job — are these three separate services or one monolith? What are the cold-start SLOs for each?
- Will the FFmpeg export job run as a **Cloud Run Job** (batch, one-shot) or a long-running **Cloud Run Service** with a task queue? These have different concurrency, timeout, and billing models.
- What is the maximum **request timeout** required? Cloud Run max is 3,600 s. FFmpeg renders on large storyboards may approach this — is there a slide count ceiling, and what happens when it is exceeded?
- Is **HTTP/2 or gRPC** needed for any service-to-service call, or is REST over HTTPS sufficient throughout?

### 1.2 Scaling & Traffic
- What are the **expected concurrent users** at steady state and peak? This drives `--max-instances` ceilings and `--min-instances` decisions beyond the export service.
- Has a **concurrency per instance** value been set per service? Cloud Run default is 80. The FFmpeg job should be 1.
- Is there a **Serverless VPC Access connector** requirement? Required if Firestore/GCS traffic must stay on Google's private network for compliance.
- Who manages **domain mapping**? Will services run on `*.run.app` URLs or custom domains with managed SSL certs? Custom domains require Cloud Run domain mapping or a load balancer.

## 2. Networking & Ingress

### 2.1 Load Balancing
- Is there a **Cloud Load Balancer (CLB)** in front of Cloud Run, or does traffic go directly to Cloud Run managed URLs? A CLB is required for: custom domains with a single IP, Cloud Armor WAF, CDN for static assets, and header-based routing.
- If a CLB is used, what **backend type** is configured — serverless NEG (Network Endpoint Group)? This affects health checks and IAM wiring.
- Is **Cloud Armor** required? The sprint plan logs 401/403 events but has no WAF, DDoS, or IP-based rate limiting at the network layer. For a platform storing screenshots of customer GTM/GA4 configs this is a significant gap.

### 2.2 DNS & TLS
- What **DNS provider** is used? Is Cloud DNS authoritative, or an external registrar?
- Are **managed SSL certificates** via Google-managed certs, or will Let's Encrypt/Certbot be used?
- Should the Admin Portal and Analyst/ID workspaces be on separate subdomains (e.g., `admin.thehammer.io`, `analyst.thehammer.io`) or path-routed under one domain?

### 2.3 CORS & Extension Origins
- The Chrome extension calls the backend API. What is the **allowed origin list** for CORS? `chrome-extension://<id>` origins must be explicitly whitelisted — this is frequently missed in production.
- Will the extension ID be **stable** (locked via the CRX key) or will it change on re-publish, breaking CORS configs silently?

## 3. Identity & Access Management (IAM)

### 3.1 Service Account Architecture
- How many **service accounts** will exist and what is each one's minimum-privilege role set? The sprint plan implies at minimum: Cloud Run backend SA, FFmpeg export SA, Admin Portal frontend read SA — none are explicitly specified.
- Does the Cloud Run backend SA have **Firestore Admin** or **Firestore User**? Over-privileged SAs are the most common root cause of GCP production incidents.
- Is **Workload Identity Federation** used for CI/CD (GitHub Actions / Cloud Build), or are service account key JSON files being committed or stored in local files?

### 3.2 API Key Architecture (Sprint 9)
- The plan defers the Secret Manager vs Firestore `api_keys` collection decision to Sprint 9.1. Specific open questions:
  - What is the key **rotation policy**? Sprint 9 states "quarterly" — is this automated via Cloud Scheduler + Cloud Function, or manual?
  - Are API keys **hashed at rest** (e.g., SHA-256 of the raw key stored, never the raw key itself), or stored in plaintext?
  - Is there a **key issuance workflow** — self-serve, admin-issued, or both?
  - What happens to in-flight requests during a rotation? Is there a **grace period** (e.g., old key valid for 24 h after new key is issued)?

### 3.3 Admin Portal Authentication
- The Admin Portal is a web app. What protects it at the browser level? The sprint plan describes only an API-key header check suitable for programmatic clients. For a web portal, is **Firebase Auth, Google SSO, or Cloud IAP (Identity-Aware Proxy)** in front of it?
- If IAP is used, it replaces the custom auth guard middleware entirely and adds Google account-level auth at zero additional code cost.

## 4. Data & Firestore

### 4.1 Data Model Completeness
- No **schema version or migration strategy** is documented. How will Firestore document shape changes be handled when a sprint renames a field?
- Are `uploads` documents **scoped to a project** via a flat `projectId` field, or stored as a **subcollection** under `projects/{projectId}/uploads`? This decision fundamentally affects query patterns, security rules, and GCS-to-Firestore referential integrity.
- What is the **expected document volume** per collection at 12 months? Firestore free tier caps at 1 GB; composite index and egress costs change materially at scale.
- Are any collections expected to require **Firestore transactions** — e.g., decrementing a quota counter and writing a membership doc atomically?

### 4.2 Querying & Indexes
- The activity feed requires a composite index on `projectId + tool + uploadedAt`. Are **all composite indexes** documented and checked into `firestore.indexes.json`? Missing indexes cause silent query failures in production — Firestore degrades to a full collection scan or returns an error.
- Does the analytics dashboard use **Firestore aggregation queries** (COUNT, SUM) or client-side counting? Aggregation queries are billed per query and have separate quota limits.
- Is **Firestore in Native mode** confirmed (not Datastore mode)? This cannot be changed after project creation.

### 4.3 Backup & Recovery
- Is **Firestore PITR (Point-in-Time Recovery)** enabled? It is off by default. What is the target RPO?
- Is there a **scheduled Firestore export to GCS** for offline analytics and disaster recovery? This is separate from PITR.
- What is the **data retention policy** for `uploads`, `session_events`, and `inactivity_events`? The sprint plan sets a 90-day lifecycle on GCS `exports/` — is there an equivalent Firestore TTL field on time-series documents?

## 5. Storage (GCS)

### 5.1 Bucket Architecture
- How many **GCS buckets** are there? The sprint plan implies at least: screenshot captures, FFmpeg exports, analyst reports. Are these in one bucket with path prefixes, or separate buckets?
- Separate buckets are strongly recommended for **independent IAM, lifecycle rules, and CORS configs**. A single bucket cannot differentiate the Admin Portal (needs thumbnail read) from the Analyst engine (needs report write) at the bucket-policy level.
- What **storage class** is appropriate? `STANDARD` for active data is correct, but completed reports and exports older than 30 days should transition to `NEARLINE` or `COLDLINE` via lifecycle rules — not just delete at 90 days.

### 5.2 Access Patterns
- Are **signed URLs** the only access mechanism, or are any objects public? If any bucket has public access, that must be an explicit, documented security decision.
- What is the **signed URL lifetime** strategy? The sprint plan uses 1-hour for exports and 9-minute refresh for thumbnails. Are these values from a threat model or arbitrary? Longer URLs increase blast radius if a URL is leaked.
- Does the **Chrome extension** write directly to GCS via a signed upload URL, or POST to Cloud Run which then writes to GCS? The current plan implies the latter — correct for auditability, but has this been benchmarked under real network conditions (mobile hotspot, VPN)?

### 5.3 Screenshot Quality & Size
- What is the **expected average screenshot file size**? This drives GCS storage cost, signed URL timeout sizing, and FFmpeg render time estimates.
- Is **lossless PNG** or **lossy WebP/JPEG** the capture format? WebP reduces storage 25–35% but requires format detection in the FFmpeg pipeline and may reduce OCR accuracy.

## 6. Observability & SRE

### 6.1 SLIs and SLOs
**No SLOs are defined anywhere in the sprint plan.** Without SLOs, the Cloud Monitoring alert thresholds in Sprint 9 have no calibration basis. Define at minimum:
- Capture endpoint: **availability SLO** (e.g., 99.5%) and **latency SLO** (e.g., p99 < 2 s)
- Report generation: **completion SLO** (e.g., 95% of reports complete within 5 min)
- Video export: **completion SLO** (e.g., 90% of exports complete within 10 min)
- Admin Portal: **availability SLO** (e.g., 99.0%)

### 6.2 Logging
- Are **structured JSON logs** emitted from all Cloud Run services? Unstructured logs cannot be efficiently queried or alerted on in Cloud Logging.
- What is the **log retention policy**? Cloud Logging default `_Default` bucket retains 30 days. Audit logs (401/403, key access, role changes) should be retained longer for security compliance.
- Are **trace IDs** propagated across service boundaries (backend API → FFmpeg job → GCS write) for end-to-end request tracing in Cloud Trace?

### 6.3 Alerting Gaps
The sprint plan defines two alerts. Missing:
- Cloud Run **error rate > X%** (4xx and 5xx separately)
- Cloud Run **p99 latency > Y ms** on the capture endpoint
- **GCS 403 errors** at scale (broken signed URLs)
- **Firestore quota exhaustion** (reads/writes/deletes per day)
- **Secret Manager access failures** (role key lookup failing silently returns a 500, not a 403 — difficult to diagnose without an alert)
- **Cold start rate** on the export service

### 6.4 Error Budget & Incident Process
- Is there an **incident response runbook**? Minimum viable runbook: how to roll back a Cloud Run revision, how to manually flush a stuck export job, how to revoke a compromised API key immediately.
- Is **Cloud Run traffic splitting** used for canary deployments (e.g., 10% to new revision) or is every deploy a hard 100% cutover?

## 7. CI/CD & Infrastructure as Code

### 7.1 Pipeline
- The plan references `deploy.ps1` (PowerShell). Is this the **only deployment mechanism**, or is there a Cloud Build or GitHub Actions pipeline?
- Manual PowerShell deploys to production are a significant operational risk. Is there a **PR-gated CI/CD pipeline** with automatic deploy on merge to `main` and protection rules on the `main` branch?
- Is **Container Registry or Artifact Registry** used for Docker images? Container Registry is deprecated; Artifact Registry is the current GCP standard.

### 7.2 Infrastructure as Code
- Is any GCP infrastructure defined in **Terraform, Pulumi, or gcloud declarative configs**? The sprint plan implies all resources are created imperatively via `gcloud` CLI commands. Without IaC there is no drift detection, no reproducible environment creation, and no PR-based review of infrastructure changes.
- At minimum, should the following be tracked as IaC: Cloud Run service configs, GCS bucket policies and lifecycle rules, Firestore indexes (`firestore.indexes.json`), IAM bindings, Secret Manager secret names and rotation schedules?

### 7.3 Environments
- Are there separate **dev, staging, and production GCP projects**? A single shared project means a bad deploy, a Firestore index rebuild, or an accidental `gcloud run deploy` can affect production data directly.
- How are **environment-specific configuration values** managed — separate Secret Manager secrets per project, or `.env` files per environment?

## 8. Security & Compliance

### 8.1 Secrets Management
- Have all files in the repo been **scanned for committed secrets** (API keys, service account JSON, `.env` files)? The GitHub MCP `run_secret_scanning` tool is available for this.
- Is **Secret Manager versioning** used? On rotation, is the previous version disabled or destroyed, and after what delay?
- Are **Secret Manager access audit logs** reviewed? Every `accessSecretVersion` call is logged — is anyone reviewing them or alerting on anomalous access patterns?

### 8.2 Data Privacy
- Screenshots may capture **PII** — usernames, email addresses in browser tabs, form field content, customer data in GTM/GA4 dashboards. Is there a documented **data classification policy**?
- Is there a **data processing agreement (DPA)** in place for GCP services? Required for GDPR if any EU users are on the platform.
- Where is **data residency** required? GCP multi-region Firestore and GCS store data across multiple regions; single-region configurations may be required for compliance.
- Are screenshots **scanned for PII before storage** using Cloud DLP, or is PII handling out of scope for the current build?

### 8.3 Network Security
- Is **Private Google Access** enabled so GCS and Firestore traffic stays on Google's private network rather than traversing the public internet?
- Should Cloud Run services other than the capture endpoint and Admin Portal be **restricted to internal ingress only**, blocking direct internet access?
- Is **Binary Authorization** considered to enforce that only images built by the CI pipeline can be deployed to Cloud Run?

## 9. Chrome Extension

### 9.1 MV3 Service Worker Lifecycle
- What is the **service worker keep-alive strategy** during an active capture session? MV3 service workers terminate after approximately 30 s of inactivity — does the extension use a keep-alive port trick or `chrome.storage.session` to survive?
- If the service worker is killed mid-session, is the **partial session state** (`sessionId`, `firstCapturePath`, capture count) recoverable, or is the session summary record permanently incomplete?
- How does the extension handle `chrome.runtime.onUpdateAvailable`? An extension update during an active session should not silently terminate the session or lose in-flight data.

### 9.2 Distribution
- Is the extension distributed via the **Chrome Web Store** (1–3 day review cycle on updates) or via **enterprise policy sideloading** (instant deployment, no review, requires Google Workspace admin)?
- For a B2B internal tooling use case, enterprise sideloading is strongly preferred — has this been formally decided?
- If Chrome Web Store is used, is the **CRX key** stored securely so the extension ID is stable across republishes (required for stable CORS configs)?

## 10. Cost Model

- Has a **GCP cost estimate** been produced for steady-state and peak load? Key cost drivers not yet quantified:
  - Cloud Run invocations/day per service and average CPU/memory per request (especially FFmpeg)
  - GCS storage GB/month and egress GB/month (signed URL reads count as billable egress)
  - Firestore reads/writes/deletes per day
  - Vision API / OCR API calls per day (Sprint 6S must produce this number)
  - Secret Manager API calls per day (every authenticated API request reads a key)
- Is there a **GCP Billing budget alert** on the project? A runaway FFmpeg loop or OCR batch job can generate a large surprise bill with no automatic cutoff.
- Is **committed use** or **sustained use discounts** applicable to any Cloud Run services with predictable baseline traffic?
